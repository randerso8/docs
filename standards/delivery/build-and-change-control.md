# Builds configuration and change delivery

> Draft for Software Engineering team review. These are proposed requirements and guidance, not an approved standard.

## Scope

Apply to the path from reviewed source to executable application and runtime configuration. The controls can be exercised locally and later automated by a selected build service. GitHub, a particular CI product, containers, and a cloud platform are not prerequisites for these proposed controls.

### DEL-BUILD-001 — Traceable build inputs and outputs

A release candidate MUST identify an immutable source revision, toolchain/runtime versions, resolved dependency inputs, build instructions, and resulting artifact identity/digest. Promote the same identified artifact through validation stages rather than silently rebuilding different bits for each environment. Where byte-for-byte reproduction is not achievable, record the cause and the alternative provenance evidence.

Evidence: another engineer can identify and rebuild the candidate from its declared inputs and compare the result or documented nondeterminism.

### DEL-BUILD-002 — Supported dependencies and accountable updates

Applications MUST inventory direct/transitive runtime dependencies, define how support/security status is evaluated, and assign ownership for updates. Pin inputs through an appropriate lock/resolution mechanism and review meaningful changes. A version is not approved solely because it is newest or generated by a tool. Findings have a risk decision, remediation owner, and deadline appropriate to the actual exposure.

Evidence: dependency inventory, an example update review, and recorded disposition of material findings.

### DEL-BUILD-003 — Explicit environment configuration

Runtime configuration MUST have a documented contract, environment-specific values/references, validation, and an accountable owner. Detect missing/invalid required values before accepting affected work. Apply SEC-BASE-003 for secrets. Separate build-time and runtime settings, especially values compiled into browser assets, and identify how changing them affects artifact identity.

Evidence: configuration schema/inventory and a controlled deployment with a deliberately invalid setting.

### DEL-BUILD-004 — Reviewed compatible deployment and recovery

Changes MUST have the relevant TEST-EVID-001 evidence, a deployment plan, and a safe recovery path. Coordinate application and schema versions using DATA-STORE-002, including coexistence during rollout. Identify irreversible operations and a forward-fix/restore plan rather than promising that every release can be rolled back automatically.

Evidence: a representative upgrade and failed-change recovery exercise with an accountable operator.

### DEL-BUILD-005 — Recorded promotion authority

Movement of a candidate into an environment with production-like effects MUST record who authorized it, what source/artifact/configuration was used, applicable evidence, and the resulting deployment state. Human review is accountable even when execution is automated. Build agents and deployment identities receive only scoped permissions under the security baseline.

Evidence: a release/deployment record that can be reconciled with running artifact and configuration identities. During local drafting, use synthetic rehearsal records rather than claiming a real production promotion.

## Rationale and open decisions

The proposal connects source review, evidence, dependencies, artifacts, and operations without selecting hosting. Choose build tooling, support policy, artifact storage, production authority, and deployment strategy before claiming implementation. [NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final) informs the lifecycle framing; these requirements are proposed team policy.
